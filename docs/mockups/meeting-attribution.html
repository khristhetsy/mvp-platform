Why Meetings reads 0 when you are getting meetings

Social Media Hub → Command Center · traced through the code · mockup of the fix options

The cause, in one line

A booking is only ever attributed if the person walked the /fit funnel first, in the same browser, before booking. Your meetings do not come that way — so the Meetings ring is not undercounting, it is counting a path almost nobody takes.

The whole chain hangs on one line: book/route.ts:99 reads an fs_session cookie, and only if it finds one calls handoffFitSession, which is the only code anywhere that writes lead_source = source_tag. No cookie, no attribution, ever.

/schedule/[hostId] reads no ?src= and no utm_* — I grepped it, there is nothing. And scheduling_bookings has no source column at all. So a direct scheduler booking carries no record of where the person came from, and nothing downstream can recover it.

The two paths a booking can take

✓ Counted — the /fit funnel path

1Clicks a tagged link → lands on icapos.com/fit?src=…
2fit_sessions row created with source_tag; fs_session cookie set
3Completes the funnel, then books in the same browser
4handoffFitSession writes overrides.lead_source = source_tag
5Funnel joins booking → contact → tag. Meetings +1
Works. Rarely happens.

✕ Invisible — every other path

1Sees the post, DMs you, or clicks straight to the scheduler
2Lands on /schedule/khris — no source captured
3Books. No fs_session cookie exists
4handoffFitSession never runs. Nothing written
5Booking has no contact link and no tag. Meetings +0
This is where your meetings are.
Two smaller breaks underneath, worth knowing about
WhereWhat it doesEffect
book.ts:131 Looks up an existing contact by email. It is a read, never an upsert — a cold lead who is not already in the CRM gets contact_crm_id = null. Meeting can never be attributed, even retroactively.
book.ts:139 Fills lead_source from the free-text answer to “How did you hear about us?” — so it stores "LinkedIn". The funnel needs exact equality with linkedin-icapos-sept. "LinkedIn" never matches.
Four ways to fix it — they stack, they are not either/or

Options

A + B are the real fix · C and D catch the remainder
A

Tag the scheduler link itself Core

/schedule/khris?src=linkedin-sept — the page reads src and the booking stores it on the row. Every link you control gets tagged: the social bio, the post CTA, your email signature, the QR on a slide.

Needs a source_tag column on scheduling_bookings. The funnel then reads the booking directly instead of going through the contact.

CatchesAnyone who clicks a link you posted
MissesDMs, word of mouth, someone typing the URL
B

Last-touch cookie on any landing Core

Set a source cookie whenever any page on icapos.com is opened with ?src= or utm_* — not only /fit. Read it at booking time. Someone who lands on the homepage from your post, browses, then books two days later still gets attributed.

This is the piece that makes A worth having: it generalises the fs_session mechanism that already works to the whole site.

CatchesAnyone who arrived from a tagged link, any page, any time in the window
MissesDifferent device, cleared cookies
C

Make “How did you hear about us?” a real picklist Useful

Today it is free text that lands in lead_source and matches nothing. Make it a fixed list whose options map to campaigns — LinkedIn → the LinkedIn campaign, not the literal string.

Self-reported, so treat it as a second-best signal: it should never overwrite a tag captured from an actual click.

CatchesDMs, word of mouth, offline — the ones A and B cannot see
MissesWhoever skips the question or guesses
D

Let staff set the source on a booking Backstop

A source field on the booking in Sales Hub → Bookings. You sat in the meeting; you know where they came from. One dropdown after the call.

Unglamorous, but it is the only thing that will ever attribute “Johnny mentioned us to someone at a conference.”

CatchesEverything, if somebody does it
MissesWhatever nobody gets round to
What A + B look like in the data
The booking becomes the attributed record, instead of the attribution being inferred through a contact that may not exist. The funnel's Meetings query gets simpler and stops depending on email equality. 
-- the column that does not exist today
alter table public.scheduling_bookings
  add column source_tag text;          -- captured at booking, first-touch wins

-- Meetings, after: one join, no email matching, no contact required
select source_tag, count(*)
  from public.scheduling_bookings
 where created_at >= $1 and created_at < $2
   and source_tag is not null
 group by 1;

-- Meetings, today: contact must exist AND its lead_source must equal the tag
--                 AND its email must equal the booker's email
One thing the dashboard should say in the meantime, and does not. “Meetings 0 of 0 · no goal” reads as no meetings happened. What is true is no meetings could be attributed — those are different facts and only one of them is alarming. Until the capture exists, that tile should say unmeasured, the way the CRR tiles do when a company has never been scored, and name the reason.

Why the Clicks number is real but the Meetings number is not. Clicks come from social_clicks, which the post's own tagged link writes directly — no identity needed, so it works. Meetings need a person to be joined across two systems, and the join key is only ever created by the /fit funnel. The 14 clicks are genuine; the funnel's “Clicks → Meetings 0.0%, your weakest step” is measuring the gap in the plumbing, not a gap in your marketing.

Worth deciding before anything is built. Whether attribution should be first-touch (the post that first brought them in) or last-touch (the one that brought them back to book). The existing /fit code preserves first-touch — if (!overrides.lead_source) — so matching that everywhere keeps one rule rather than two.
