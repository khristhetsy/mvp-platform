Notify me of all activity on founder & investor accounts

Mockup · admin notification settings + the feed it would draw from

What I found before designing this

The table exists. Almost nothing writes to it. operational_activity_events is fully built — categories, severities, visibility, dedupe, a feed query layer in src/lib/operational-activity/. But of the 115 founder and investor API routes, only 6 emit an event: onboarding, two learning routes, intro-requests, saved-deals, interests.

So today a founder can change their funding ask, re-upload a pitch deck, edit their cap table, invite a co-founder, publish a campaign or delete a data-room file and nothing is recorded anywhere. The ten notification event keys you already have (document_uploaded, investor_interest, …) are business milestones, not account activity.

This is therefore not a notification problem. There is nothing to notify from. The work is: instrument the write paths first, then the feed and the alerts fall out of it for free.

4 · How 109 routes get instrumented without touching 109 files by hand
One wrapper at the route boundary. It reads the actor from the session, the entity from the path, and the before/after from the Supabase write — so a route opts in with a single line rather than a bespoke createOperationalEvent call it will forget to keep current. 
// src/lib/operational-activity/with-activity.ts  (new)
export function withActivity(handler, spec) {
  return async (req, ctx) => {
    const before = spec.snapshot ? await spec.snapshot(ctx) : null;
    const res = await handler(req, ctx);
    if (res.ok) emitOperationalEvent({
      eventType: spec.type,                 // "founder.funding_amount_changed"
      eventCategory: spec.category,
      actorUserId: ctx.userId, actorRole: ctx.role,
      severity: spec.severity,              // destructive → "high"
      metadata: diff(before, await spec.snapshot?.(ctx)),
      sourceModule: spec.module,
    });                                      // fire-and-forget; never blocks the response
    return res;
  };
}

// src/app/api/founder/settings/route.ts
export const PATCH = withActivity(handler, {
  type: "founder.profile_updated", category: "founder",
  module: "founder-settings", severity: "low",
  snapshot: (ctx) => loadCompany(ctx.companyId),
});
Order this would go in. Wrapper + the diff helper; then the ~30 routes that carry real meaning (profile, documents, data room, cap table, campaign, interests, intro requests, access changes) rather than all 109 at once — page views and autosaves are noise and would bury the six things you actually want to see. Then the feed page, then the six preference rows.

One thing to decide, because it changes the schema. A diff ("$750,000 → $400,000") is far more useful than a bare "profile updated", but it means storing the old value in metadata. That is founder-supplied business data sitting in a second table with its own retention. Either it is in scope and sanitize.ts gets a field allow-list, or events stay field-name-only and the feed says "changed the capital ask" without the numbers.

Not included on purpose. Sign-in events come from Supabase Auth, not from a route — those need the auth.audit_log_entries mirror or a webhook, which is a separate piece of work from instrumenting the API surface.
