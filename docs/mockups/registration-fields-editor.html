Registration fields — admin editor

Admin → Event Hub → Registration fields · mockup, nothing built

Today these live only in code. lib/icfo-events/registration-fields.ts exports three arrays that both the public registration form and the admin “Register a guest” form read, so they can never drift. Changing a check-size band means a deploy.

This is the same problem crr_weight_sets and pricing_sets already solved: move the definition into a versioned table, keep one active row, append on save, and seed it from today’s code constants so nothing changes on the day it ships.

Sectors stay linked rather than copied. That row’s options come from EVENT_SECTORS, the same list the event’s own sector tracks use — the chips on your screenshot are that list. Letting someone edit them here would create a second sector vocabulary that silently diverges from the one events are tagged with, so the row shows Options linked and points at the sector settings instead.
The key is the part that can quietly destroy data, so the editor treats it as load-bearing. Answers are stored in registrations.answers as jsonb keyed by field key. A rename leaves every previous answer stranded under the old key — invisible in the UI, still in the database, absent from exports.
  • Never answered → key is editable, because nothing points at it yet.
  • Answered by anyone → key is locked, and the editor says how many. The label stays free to change, which is what people usually actually want.
  • Removing a field hides it from the form but keeps the answers. Exports keep the column so historical registrations stay readable.

One decision before this gets built: global, or per event? Today there is exactly one set, shared by every event, because it lives in one file.
  • Global only (what the mockup shows) — one set, versioned. Simplest, and matches how pricing and CRR weights already work. An expo and a webinar ask identical questions.
  • Global + per-event override — an event can opt out and define its own. More flexible, but two places to look when a field is wrong, and exports across events stop lining up.
I’d start global. The per-event case is real but rarer than it sounds, and it can be added later without changing the table — an event_id column that is null for the shared set.
PieceNotes
Migration registration_field_sets — version, roles jsonb, common jsonb, by_type jsonb, is_active, reason, created_by. Seeded from today’s constants so the first save changes nothing.
Loader loadRegistrationFields(), cached per request like loadPricing(), falling back to the code constants when the table is empty or unreachable — the form must never fail to render.
Answer counts One query per key over registrations.answers to decide which keys lock. This is what makes the guard real rather than advisory.
The three consumers EventRegistrationForm, EventManualRegister, EventRegistrationsBoard already read the arrays — they take the loaded set instead, and otherwise don’t change.
