Label audit — Preparation complete & Capital Readiness Rating (CRR)

Every surface, every account type · mockup — nothing built

The problem: two different numbers, eleven different names

A · the completion measure

Preparation complete

computeReadinessScore(uploadedTypeCodes) · gate 75

A count of how many required document types are present. Not a rating — no factor, no dimension, no weight touches it. Re-scoring cannot move it.
Called today: Readiness qualifiedCompletion ≥ 75%CompletionReadiness scoreReadiness

B · the rating

Capital Readiness Rating (CRR)

crrFor(companyId) · gate 65 (OUTREACH_GATE)

The 13-factor engine score on the company's own stage profile. The number the Weights tab tunes and the outreach gate reads.
Called today: Capital Readiness RatingCapital ReadinessCapital Readiness ScoreReadiness ratingReadiness signalReadinessReadiness band
The word “Readiness” alone is currently used for both. The founder dashboard tile reads label: "Readiness" over the engine score, while DiligenceReportCompare reads “Readiness score” over the document count. Same word, two numbers, different gates — and a founder comparing the two pages has no way to tell. This is what the rename fixes; it is not a cosmetic pass.

5 · Public marketing site

18 places across src/content/**, (marketing)/**, deals/page.tsx and the OG images say Capital Readiness Rating. They are all B, all already correct, and none of them mention the completion measure — a visitor has no account, so A does not exist for them.

Two exceptions worth a look: deals/page.tsx:32 says “Capital Readiness Score” where everywhere else says Rating; and (marketing)/readiness/page.tsx uses the bare word “readiness” as running prose (“readiness is what iCapOS produces”), which reads fine and should stay — this audit is about labels on numbers, not the English word.

6 · Related fields — what deliberately stays as it is
IdentifierWhy it keeps its name
profiles.journey_stage · 'qualify' The stage key is qualify in the database and Preparation in the UI — that mapping already exists in STAGE_META. Renaming the key touches migrations for no user-visible gain.
StageConditions.readinessQualified Field key, not a label. Renaming it touches 14 files and changes nothing anyone sees. Only the display string moves.
company_readiness_scores · readiness_score Table and column names. The reader is crrFor(); what it is called on screen is set in one place above.
computeReadinessScore() Function name. Its output is now labelled “Preparation complete” everywhere. A comment on the function saying so is enough.
readinessBand · anonymized-cards.ts:18 API field consumed by investor match cards. The field stays; the visible label above it becomes CRR.
lib/prescore/rubric.ts The lead pre-score. Its own comment already forbids calling it CRR — leave it entirely alone, and do not let “CRR” leak into voice or approach copy.
How this stops drifting again. src/lib/crm/lexicon.ts already locks capitalReadiness: "Capital Readiness Rating" and has a unit test that fails the build if a forbidden term appears — but it only polices components/crm/**. Extending the same pattern is the smallest durable fix:
  • Add crrShort: "CRR" and preparationComplete: "Preparation complete" to the lexicon.
  • Add the bare string "Readiness qualified" to a forbidden list, plus bare "Readiness" as a standalone label, so the ambiguous word cannot come back as a column header or tile label.
  • Widen the existing lexicon test from components/crm/** to every founder, investor and admin surface in the tables above.
Without that, the next dashboard adds a twelfth name.
Three genuine bugs this audit turned up, separate from the renaming:
  • stage-menu-mirror.ts:64 — an item labelled Capital Readiness Rating whose condition reads the document count. The founder is told a CRR requirement is met when what was measured was file uploads.
  • stage-gate-reminders.ts:46 — an email telling the founder to raise their “Capital Readiness score to 75” when the gate it belongs to is the document count and the CRR gate is 65.
  • CapitalReadinessSection.tsx:284 — the CRR explanation still describes the retired 60/30/+5/+5 formula, so a founder following it will do work that cannot move the number.
Each is a wrong statement to a user, not a style inconsistency.
