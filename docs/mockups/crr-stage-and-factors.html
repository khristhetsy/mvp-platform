3. Stage → profile, said out loud

The mapping you described is already what the code does — it reads companies.funding_stage, normalises it, and picks the profile. What is missing is that no screen says so, so the Weights tab looks like four abstract presets rather than four real cohorts. This adds a mapping strip under the profile tabs and a count of who is actually in each.

Taken from each company’s Funding stage. A founder who has not set one is scored as Seed. Change a company’s stage and its score moves to that profile at the next re-score.

What a founder sees vs. what an investor sees. The founder’s own score uses their stage profile — a pre-seed founder is not judged on Series A traction weights. Investor-facing surfaces all read the Series A profile instead, so one company can be compared to another. Both numbers are already stored per company; nothing is recomputed.
One thing to fix while we are here. There are two copies of this mapping. The canonical one (normalizeFundingStage) understands “pre-seed”, “preseed”, “idea”, “angel”, “series-b/c/d”, “growth”, “expansion”, “bridge”, “pre-IPO”. The weights preview (weight-sets-db.ts) has its own shorter version that matches on stage.includes("a") — so a company whose stage is written “Angel” lands in the wrong bucket in the impact preview. The fix is to delete the second copy and call the first.

Small

  • Pre-seed rename — one label map, plus the traction-floor heading. No migration, no data change.
  • Stage mapping strip — the counts come from a query already being run; the mapping text is static.
  • Delete the duplicate mapping — replace nine lines with a call to the existing function, and add the case it gets wrong to the test file.

Needs a decision from you

  • “View the detail” — I read that as the existing factor popup, now obviously clickable. If you meant jump to the company’s own page instead, say so and the chip becomes a link.
